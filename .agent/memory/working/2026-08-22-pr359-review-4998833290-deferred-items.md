## Deferred #1: ssrf_pinned_adapter.py's shared connection_pool_kw race

**Not the same bug as the PoolKey crash already fixed this session** (see
[[lesson_c8beaa402e84]]) -- that was a hard crash on ANY real request,
already fixed via a custom `key_fn_by_scheme` normalizer. This is a
different, subtler issue that survives the crash fix:

`SSRFPinnedHTTPAdapter.send()` does
`self.poolmanager.connection_pool_kw.update(pool_kwargs)` (mutating a
**shared, instance-level dict**) before calling `super().send()`, then
resets it in a `finally` block. If the **same adapter/session instance** is
used concurrently across threads (or even sequentially interleaved via
async/greenlets), thread A's `pinned_ip` can be overwritten by thread B's
between A's `update()` call and whatever code inside `super().send()` reads
`self.poolmanager.connection_pool_kw` for A's connection -- pinning to the
wrong IP, which is a real SSRF-relevant correctness bug (not just a data
race), since the whole point of pinning is connecting to the specific IP
that was DNS-resolved-and-validated for THIS request.

**Why not fixed in this pass:** this needs one of a few real design
decisions, not a quick patch:
- Thread-local `connection_pool_kw` overrides instead of a shared instance
  dict (matches how `contextvars`/`threading.local` are usually used for
  this exact pattern).
- Per-pin pool-key inclusion so concurrent pins to different IPs for the
  same host genuinely get separate pools (partially already true post-fix,
  since `pinned_ip` IS still part of the unfiltered `request_context` that
  reaches `_new_pool` -- but the WINDOW between `.update()` and the pool
  lookup is still shared-state-vulnerable).
- Or: document that `ssrf_session()`/`ssrf_request()` are not safe to share
  across concurrent callers and each caller must create its own session
  (cheapest fix, but weakens the module's usefulness as a connection-reuse
  transport).

Needs a design pass + explicit user sign-off before touching it, per this
session's established discipline on security-critical concurrency changes
(not a "rush it" caution -- getting this wrong silently reintroduces the
exact TOCTOU class this module exists to close).

## Deferred #2: orchestrator/orama_bridge.py loopback routing

CodeRabbit (likely `#discussion_r3834992462`, "SSRF tightening" -- the user
named this URL but the fork's fetch mapped it to a Major/Heavy-lift finding
on `orama_bridge.py:68-72`, not yet independently confirmed against the
exact discussion thread text): classify endpoints via
`validate_model_endpoint_url(..., allow_public=False)` and route
validated local/loopback endpoints through direct local transport (not
`ssrf_request`, which is deny-by-default and would reject them), keeping
`ssrf_request` only for genuinely remote endpoints; add a loopback
integration test exercising the real transport.

This mirrors the already-fixed pattern in `orchestrator/connectivity.py`
(split into `_probe`/`_probe_local`, see [[lesson session `f6b92e2bd7f5`]]
from the prior PR #359 batch) -- `orama_bridge.py` apparently still routes
everything through the deny-by-default path. **Not fixed here**: this is a
real architectural change to a file already touched multiple times this
session (async httpx removal, `asyncio.to_thread(ssrf_request, ...)`
wiring) -- needs the exact discussion thread's text confirmed first (the
fork's summary was a paraphrase, not a verbatim quote) before writing the
actual split, to avoid re-deriving connectivity.py's fix from a possibly
imprecise restatement.
